# Rapport — Portage du test PIBT vers 5 DotBots réels

**Date :** 2026-06-09
**Objet :** Adapter le démo PIBT (qui tournait en simulateur) pour piloter 5 DotBots
réels, comme le faisait le code démo en simulation.

---

## 1. Contexte & diagnostic

`dotbot_pibt_demo.py` calcule des trajectoires PIBT (grille 8×8, cell=500 mm,
carte 4000×4000 mm) et les envoie en waypoints via l'**API REST** du contrôleur
(`http://localhost:8000`). Le script est **agnostique au transport** : il ne fait que
du REST/HTTP et auto-détecte le nombre de bots.

Constats clés :
- La navigation par waypoints s'exécute **à bord du firmware** de chaque DotBot
  (boucle de contrôle onboard sur position LH2). Le contrôleur ne fait que pousser
  waypoints + calibration. → côté script, **rien à changer pour le transport**.
- Le contrôleur initialement actif sur :8000 était **le simulateur** (10 bots aux
  adresses de `simulator_init_state.toml`).
- **Positions de départ aléatoires** : déjà gérées — `get_grid_state()` lit la position
  LH2 réelle courante de chaque bot et construit les agents PIBT sur ces cases mesurées ;
  `resolve_conflicts()` décale deux bots tombant dans la même case.
- **Risque réel identifié** : envoyer tout le chemin d'un coup casse la garantie
  anti-collision de PIBT, qui suppose un avancement **synchronisé** (lock-step). Sur
  du matériel asynchrone, deux bots peuvent occuper une même case au même instant.

## 2. Travaux réalisés

### 2.1 Durcissement du code (Partie B)
Réécriture du cœur du démo pour une **exécution pas-à-pas synchronisée** :
- `build_pibt()` remplace `run_pibt()` : expose `sim`/`agents`/`addresses` pour piloter
  l'exécution live.
- `run_pibt_live()` : à chaque pas PIBT, envoie **un seul** waypoint par bot (sa case
  suivante), puis appelle la barrière de synchronisation.
- `wait_until_all_arrived()` : poll l'API jusqu'à ce que **tous** les bots soient à
  < `threshold` de leur case-cible ; **timeout par pas** pour éviter le blocage si un
  bot stalle (log + poursuite).
- `fetch_grid_state_with_retry()` : attend que ≥ `min-bots` soient localisés au démarrage.
- Threshold par défaut **50 → 100 mm** (< demi-case 250, > bruit LH2 ~20 mm + inertie).
- Nouveaux flags : `--step-timeout` (8 s), `--settle` (0,3 s), `--min-bots` (2).

### 2.2 Versionnage des scripts
- `dotbot_pibt_demo-v1.py` — version **simulateur** d'origine (envoi en masse, threshold 50).
- `dotbot_pibt_demo-v2rc1.py` — version **durcie** pas-à-pas (réel + simulateur).
- L'ancien `dotbot_pibt_demo.py` (non versionné) a été supprimé pour éviter la confusion.

### 2.3 Documentation

## 5. Reste à faire (Partie A — opérationnel)

1. Charger l'app DotBot complète sur la flotte puis la démarrer :
   ```bash
   dotbot swarm flash /home/dok/.dotbot/artifacts/dotbot-firmware-1.22.0/dotbot-sandbox-dotbot-v3.bin -ys
   dotbot swarm start
   ```
2. Lancer le contrôleur contre le vrai swarm (pas le simulateur) :
   ```bash
   dotbot run controller --conn mqtt://localhost:1883 --swarm-id 1234 --map-size 4000x4000
   ```
3. Vérifier `curl …/controller/dotbots` → 5 vraies adresses avec `lh2_position`.
4. Lancer le test : `python dotbot_pibt_demo-v2rc1.py --dry-run --seed 1` puis sans `--dry-run`.

### Points de vigilance
- `~/.dotbot/calibration.out` ne contient **qu'une basestation** (37 octets). Si les
  positions réelles sont incohérentes → recalibrer avec les basestations physiques.
- Démarrer petit (2 bots) avant de lancer les 5, et observer dans l'UI :8000.
